# 区间分类自动编号 —— 实施方案

## 一、背景与动机

### 问题

当前插件的标题编号是纯顺序递增的（1, 2, 3, 4…）。对于人设笔记，不同笔记中**语义相同的一级标题希望保持编号稳定**（如"反差"始终在 2 开头、"爱情线"始终在 4 开头），但复杂人设（如傲娇）的一级标题比标准人设（如天然）多出很多"特征细分"标题，导致后续标准章节的编号全部漂移。

### 核心需求

- 同一类型的笔记之间，**语义相同的章节编号稳定**（如"反差"始终是 21、"形成原因"始终是 31、"爱情线"始终是 41）
- 不同笔记中**数量不固定的"特征类"标题不影响后续章节编号**
- 规则可配置、可扩展（人设标签、人设组合等不同类型各自一套规则）
- 不影响现有的 skip / lock / repeat 功能

## 二、最终方案：区间分类编号法

### 2.1 编号公式

```
编号 = 区间ID × 10 + 区间内序号
```

- 十位数 = 区间 ID（1~7，固定）
- 个位数 = 该标题在区间内的出现顺序（**从 1 开始递增**）

### 2.2 区间划分（人设标签）

| 区间 ID | 编号范围 | 名称 | 判定方式 | 关键词 |
|---------|----------|------|----------|--------|
| 1 | 11–19 | 特征类 | **位置法** | 无（见 2.3） |
| 2 | 21–29 | 搭配标签 | 关键词匹配 | `反差`、`分类及搭配标签`、`通用搭配标签` |
| 3 | 31–39 | 深度分析 | 关键词匹配 | `适配度分析`、`形成原因`、`与其他标签的区别` |
| 4 | 41–49 | 爱情线 | 关键词匹配 | `爱情线` |
| 5 | 51–59 | 人物弧光 | 关键词匹配 | `人物弧光`、`如何改变` |
| 6 | 61–69 | 技巧 | 关键词匹配 | `技巧` |
| 7 | 71–79 | 举例 | 关键词匹配 | `举例` |

### 2.3 位置法（区间 1 的核心机制）

**问题**：特征类的标题因笔记而异，无法用固定关键词识别。

**解法**：
1. 从前往后扫描所有 H1 标题
2. 找到**第一个匹配区间 2~7 任一关键词**的标题，称为「锚点」
3. 锚点之前的**所有 H1 标题**，全部归入区间 1（特征类），按出现顺序编号为 11、12、13…

> 如果笔记没有匹配区间 2+ 关键词的标题（极小概率），则所有 H1 都归入区间 1。

### 2.5 子标题编号

H2、H3、H4 保持不变，用父标题的区间编号 + `.` 分隔的层级序号。示例：

```
# 21 反差
## 21.1 偶尔的小聪明
## 21.2 勇敢
### 21.2.1 具体案例
```

子标题编号沿用现有的 `updateHierarchicalBlocks()` 逻辑，不做修改。

## 三、触发机制：YAML Frontmatter

### 3.1 格式

笔记的前若干行为 YAML frontmatter（在 VS Code 中编辑保持标准格式）：

```yaml
---
tags: #人设标签 #人设模型
description: 
triggers: 
---
```

### 3.2 检测逻辑

1. 获取页面前若干行内容（最多 20 行，足够覆盖 frontmatter）
2. 检测是否以 `---` 开头、后续包含 `---` 结束的 YAML frontmatter 结构
3. 从 frontmatter 中提取 `tags:` 行的内容
4. 解析 tag 列表（如 `#人设标签`、`#人设模型`），去除 `#` 前缀
5. 依次与配置中的规则 tag 进行匹配，**第一个命中即生效**
6. 匹配成功 → 对该页面启用区间编号；匹配失败 → 回退到现有顺序编号

### 3.3 为什么用 tags 而不是 category

- `tags` 是更通用的元数据字段，未来可复用于 AI 写作流程
- 一个笔记可以有多个 tag，如 `tags: #人设标签 #人设模型`
- 插件的 tag 匹配采用**第一个命中即生效**策略：按配置中的规则顺序匹配，命中的第一条规则生效

## 四、规则配置存储

### 4.1 存储方式：SandboxStorage 键值对 + 索引

> Logseq 的 SandboxStorage 是 key-value 存储（类似 localStorage），不支持通配符扫描或文件系统操作。因此用「索引 key」替代文件扫描。

每条规则存储为独立的 SandboxStorage key：

| Key | Value |
|-----|-------|
| `category-rule-人设标签` | 该规则的 JSON 对象 |
| `category-rule-人设组合` | 该规则的 JSON 对象 |
| `category-rule-index` | `["人设标签", "人设组合"]` （规则名列表，用于枚举） |

### 4.2 单条规则 JSON 结构

`category-rule-人设标签` 的 value：

```json
{
  "tag": "人设标签",
  "categories": [
    {"id": 1, "name": "特征类", "positionBased": true},
    {"id": 2, "name": "搭配标签", "keywords": ["反差", "分类及搭配标签", "通用搭配标签"]},
    {"id": 3, "name": "深度分析", "keywords": ["适配度分析", "形成原因", "与其他标签的区别"]},
    {"id": 4, "name": "爱情线", "keywords": ["爱情线"]},
    {"id": 5, "name": "人物弧光", "keywords": ["人物弧光", "如何改变"]},
    {"id": 6, "name": "技巧", "keywords": ["技巧"]},
    {"id": 7, "name": "举例", "keywords": ["举例"]}
  ]
}
```

- `tag`：与此规则关联的 tag 名（与笔记 frontmatter 中的 `tags:` 值匹配）
- `categories`：区间定义数组
- `positionBased: true` 表示该区间用位置法（每个规则必须恰好一个区间为 `positionBased`，且其 `id` 必须为 1）
- 关键词匹配为**子串包含**匹配（标题文本包含关键词即命中），忽略大小写和全角/半角空格差异

### 4.3 设置面板：启用规则列表

在插件设置面板中新增一个配置项：

| 配置项 | 类型 | 说明 |
|--------|------|------|
| 启用的规则 | `string`（多行文本输入） | 每行一个 tag 名，只有列出的规则才会生效。留空则启用全部已存在的规则 |

例如「启用的规则」文本框内容：
```
人设标签
```

> **为什么不用多选列表 UI？** Logseq 插件设置 API 的原生控件只有文本框、开关、下拉单选，不支持动态多选列表。当前用文本框逐行列出是最直接的方案。后续可考虑在 Logseq 中创建专用配置页面做可视化编辑。

### 4.4 默认规则

插件首次启动时，如果 `category-rule-index` 不存在或为空数组，自动创建默认的 `category-rule-人设标签`（内容见 4.2）并将 index 设为 `["人设标签"]`。

### 4.5 规则加载流程

```
插件启动 / 设置变更：
1. 读取 category-rule-index → 得到所有存在的规则名列表
2. 读取「启用的规则」配置
3. 如果「启用的规则」为空 → 取 index 中的全部规则名
4. 如果「启用的规则」非空 → 取 index 与「启用的规则」的交集
5. 逐个读取 category-rule-{规则名} → 构建 tag → CategoryRule 映射表（内存缓存）
```

## 五、核心算法

### 5.1 页面扫描与分类

```
输入：页面所有标题块（已按文档顺序排序）
输出：分类映射 Map<区间ID, 标题数组>

步骤：
1. 初始化分类映射，每个区间 ID → 空数组
2. 找到第一个匹配区间 2+ 任一关键词的 H1 → 记为 anchorIndex
3. 遍历所有 H1 标题（从位置 0 开始）：
   a. 如果当前位置 < anchorIndex：
      → 归入区间 1（positionBased 区间）
   b. 如果当前位置 >= anchorIndex：
      → 遍历区间 2~N，用关键词匹配
      → 命中的第一个区间即为该标题的区间
      → 如果没有任何区间匹配：
         → 沿用上一个匹配成功的区间（保持连续性）
4. 返回分类映射
```

### 5.2 编号生成

```
输入：分类映射
输出：编号映射 Map<块UUID, 编号字符串>

步骤：
1. 按区间 ID 升序遍历分类映射
2. 对于每个区间内的标题数组：
   a. 初始化序号 = 1
   b. 遍历标题：
      - 如果标题状态为 skip → 跳过，不消耗序号，递归子标题
      - 如果标题状态为 lock → 提取已有编号，更新序号为提取值+1
      - 如果标题状态为 repeat → 使用上一个非 skip 标题的编号（序号不自增）
      - 否则 → 编号 = "区间ID×10 + 序号"，序号+1
   c. 更新标题文本（移除旧编号，写入新编号）
3. 递归处理子标题（沿用现有层级编号逻辑）
```

### 5.3 与现有 skip/lock/repeat 的兼容

- **skip**：标题不参与区间归类，不消耗序号。子标题仍递归处理。
- **lock**：标题参与归类，但不修改文本。从锁定标题的现有编号中提取序号，后续兄弟标题从该序号+1 继续。
- **repeat**：参与归类，但使用上一个兄弟的编号（不递增序号）。

skip/lock/repeat 的状态存储和右键菜单完全不变。

## 七、categoryRules.ts 模块设计

### 7.1 导出函数

```typescript
// 从 SandboxStorage 加载所有 category-rule-*.json 文件
// 根据「启用的规则」过滤，构建 tag → 规则的映射表
// 返回 Map<tag名, CategoryRule>
loadAllCategoryRules(): Promise<Map<string, CategoryRule>>

// 从页面首行内容中检测 YAML frontmatter，提取 tags，匹配规则
// 返回匹配到的 CategoryRule，或 null（无匹配）
detectPageCategoryRule(pageContent: string): Promise<CategoryRule | null>

// 对标题块按区间规则分类
// 返回 Map<区间ID, 标题数组>，保留标题的原始文档顺序
classifyHeadingsByCategory(
  headers: HierarchicalTocBlock[],
  rule: CategoryRule
): Map<number, HierarchicalTocBlock[]>
```

### 7.2 内部类型

```typescript
interface CategoryDef {
  id: number           // 区间 ID（1-9）
  name: string         // 区间名称（用于调试和 UI 显示）
  keywords?: string[]  // 关键词列表（positionBased 为 true 时不需要）
  positionBased?: boolean  // 是否使用位置法分类
}

interface CategoryRule {
  tag: string              // 关联的 tag 名（如 "人设标签"）
  categories: CategoryDef[]  // 区间定义数组
}
```

### 7.3 编号生成与文本更新

编号生成和文本更新逻辑**不放在 categoryRules.ts 中**，而是在 `index.ts` 的 `updateHierarchicalBlocks()` 中集成：
- 在现有流程前插入分类步骤，将 H1 标题按区间分组
- 分组后的标题仍然使用现有的 `processSiblings()` 逻辑进行编号和文本更新
- 这样最大程度复用现有代码，减少重复

## 八、测试验证

### 8.1 单元测试场景

1. **标准人设笔记**（如天然）：锚点前 1 个标题（"特征"），验证区间 1 有 1 个、区间 2+ 的正确编号
2. **复杂人设笔记**（如傲娇）：锚点前 6 个标题，验证区间 1 有 6 个（11~16），区间 2+ 不变
3. **纯特征笔记**（如高冷前 3 个标题）：验证区间 1 正确编号
4. **无 frontmatter 页面**：回退到现有顺序编号
5. **skip 在区间内**：skip 的标题不消耗序号
6. **lock 在区间内**：锁定标题不变，后续序号正确递增
7. **repeat 在区间内**：repeat 标题使用上一个兄弟的编号
8. **交叉匹配**：一个关键词出现在两个区间定义中 → 优先匹配先出现的区间

### 8.2 用户验收测试

1. 插件首次启动后，确认自动创建了 `category-rule-人设标签.json` 默认规则文件
2. 在设置面板的「启用的规则」中确认 `人设标签` 已列出
3. 打开天然笔记 → 点击重新编号 → 验证编号变为 11, 21, 22, 23, 31, 32, 41, 51, 61, 71
4. 打开傲娇笔记 → 点击重新编号 → 验证编号变为 11~16, 21~23, 31~32, 41, 51, 61, 71
5. 新建一个规则文件（如 `category-rule-写作模板.json`），在「启用的规则」中添加「写作模板」，验证新规则生效
6. 从「启用的规则」中移除某条规则，验证对应 tag 的笔记回退到顺序编号
7. 测试 skip/lock/repeat 仍然正常工作
